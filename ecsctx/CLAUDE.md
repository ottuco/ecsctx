# /ecsctx

Core structured logging module with ECS field mapping and PII/PCI masking.

## Entry Points
- `context.py` - `LoggingContext`, `logging_context` context manager, `get_trace_id()`
- `processors.py` - `contextvars_injector`, `mask_sensitive_data` (delegates to `masking.MaskPIIFilter`), `namespace_ecs_fields`
- `masking/` - Unified PII/PCI masking engine: `MaskPIIFilter` (stdlib `logging.Filter`), `install_maskers()`
- `pii/` - PII tokenization (HMAC-SHA-256) and encryption (AES-256-GCM) via keyset files

## Critical Context
- `logging_context` supports nesting - inner contexts merge with outer, auto-restored on exit
- `get_trace_id()` parses W3C traceparent format: extracts 32-char trace-id from `{version}-{trace-id}-{parent-id}-{flags}`
- `PRIMARY_KEYS` in processors.py defines which fields stay at root vs get pushed to `extra`
- Masking has two entry points, both driving the same `MaskPIIFilter`: the filter on every handler `get_logging_config()` builds (masks the record in place — Sentry's logging integration, `handleError` and handlers that never call `format()` read the record) and `mask_sensitive_data` (structlog processor, in the formatter's own chain). The second pass is cheap: `mask_by_patterns` remembers strings already known clean, and a known-clean string is not re-parsed. A string that is a JSON object or list (≤ `JSON_PARSE_LIMIT`, 64 KiB) is parsed and walked with the key rules only, re-serialised only if a key rule changed something, then content-scanned once as text — so a JSON number holding a PAN still masks, as an unquoted marker. Never scanned (`DEFAULT_SKIP_KEYS`, `masking/filters.py`): `service`/`project`/`log` and the correlation ids `session_id`, `trace`, `span`. `user.name` is exempt from the name key rule but content-scanned. The record marker stores the packs that masked it, so a filter with more packs still masks.
- Two independent detection strategies inside `MaskPIIFilter`: 17 ordered content rules (`masking/patterns.py::RULES` — order is load-bearing, see the comments above `_RULE_TABLE`), grouped into packs (`default` always on; `pci`, `financial_ids` opt-in via `masking/config.py`), each behind a literal pre-check; and key-name matching (`classify_key()`: substring on the lowercased key, fail closed, EXCEPT the three families where a substring made false positives -- a credential word must end the key (`scheme_token` yes, `schemeTokenProvisioningMode` no), `authorization` must be the whole key (`authorizationCode` is a payment verdict), and a `*name` key is a person's only if a person qualifier is in the name (`customer_name` yes, `domainName` no); a CVV word counts anywhere in the key unless its tail names something about one (`cvv_input` yes -- fail closed -- `cvv_required`/`cardSecurityCodeError` no), matched on the separator-free key; `track`/`magnetic` are SAD only when the rest of the key names the data (`raw_track` yes, `track_id` no), and a key ending in `cryptogram`/`cavv`/`ucaf` is SAD; a national id (`civil_id`, `passport`, `qid`, ...) is `ssn` in every pack; SAFE_KEYS is matched in both spellings, separators or camelCase; card keys matched precisely; expiry is NOT classified and is listed in `SAFE_KEYS`; `sad` (track data, PIN blocks, EMV images, cryptograms) is destroyed outright like CVV and can never be listed safe; cached). A matching key masks its value. A scalar under a non-exemptable type is masked whole (a PAN-shaped credential is the label, never truncated); a CONTAINER under `card`, `cvv`, `sad` or `secret` is walked per leaf (`_WALKED_TYPES`) -- unnamed leaves take the container's type, under `cvv`/`sad` nothing is weaker than the container and only a service-listed key escapes, and a card-shaped object under a credential key is walked as `card` -- spelled out in `_mask_dict` rather than made exemptable, because `exemptable` also governs path exemptions and none of these may ever be whitelistable; a `{name, value}` pair masks `value` by the strictest type its identifiers name (`_pair`); a bare `name` under a container named by a thing (`name_context`) is not a person; booleans are never masked; a dataclass/namedtuple is masked by field then rendered back to repr text; the walk stops at `_MAX_DEPTH` and any exception replaces the message with `[MASKING-FAILED: …]` (a log call must never raise); a dict/list under a PII key (`customer`, `billing`, `contact`, `name`, …) keeps its shape and each field is masked on its own — by its own key's type, kept if a safe key (`id`), else as the container's type — so per-field tokens correlate across records. `exc_info`/`stack_info` are never masked (the rendered `error.*` is). Card keys truncate a PAN value and show what is not one (`mask_card_value`: under 12 digits reads through, 12+ is content-scanned for a PAN and refused if none is found, if a run of card-number length is left beside the truncations -- a truncation's first six counting with the digits before it -- or if a Luhn-valid reading the rule leaves in free text shows more than its first six and last four, `_overexposes_a_card`). A PAN under ANY key is truncated rather than tokenized (`filters._mask_pii_leaf`, gated on `pci`): a keyed hash beside a truncation of the same PAN is what FAQ 1117 forbids, and a card number typed into the name box used to produce exactly that. Under `pci`, a value a PII, secret, ssn or payment-id key would tokenize is its label, not a token, when it holds any 12+ digit run (`holds_pan_run`, fails closed); only in a phone field is a `+`-led run of at most 15 digits (E.164) the phone number.
- A tokenized value is the bare token (`ptok:v1:…`); `[LABEL]` only where no token can stand (tokenization unconfigured/failing, or CVV/card, which are never tokenized; expiry is not masked at all). A null under a sensitive key stays null. `_WHOLE_TOKEN` keeps the credential text rules off a value that is already a token; like `already_tokenized` and `already_masked`, it takes only the exact shape `tokenize` emits (`ptok:v1:` + 43 base64url characters), so anything else typed after `ptok:` is masked. Path exemptions via `configure_masking()`, Django `ECSCTX_MASK_EXEMPT_PATHS`, or env `PII_MASK_EXEMPT_PATHS` (`masking/exemptions.py`, a pattern may start at any depth of the record) apply only to the exemptable field types (email/phone/address/name/generic) and only skip the key-based match — content rules still run on the value (defense in depth). Secrets (cvv/card/secret/payment_id/pem_key/iban/jwt/ssn) are never exemptable.
- PII tokenization supports two providers (`PII_PROVIDER=file|vault`). File provider reads mounted keysets; Vault provider authenticates via AppRole and fetches from KV v2. Access mode (`PII_ACCESS=tokenize|full`) enforces least privilege. Auto-configures lazily from env vars.
- When PII is not configured, `safe_tokenize()` (`masking/tokens.py`, re-exported from `processors`/`ecsctx`; the log-safe wrapper over `pii.tokenize`) returns `[PII_REDACTED]` — `mask_by_field_type()` catches that and falls back to `[LABEL]` rather than embedding it.

## Submodules
- `masking/` - `filters.py` (`MaskPIIFilter`, the engine), `patterns.py` (`RULES` content rules and packs, `classify_key()`, `SAFE_KEYS`), `config.py` (pack and skip-path selection), `tokens.py` (`safe_tokenize`, `mask_by_field_type`, `already_masked`), `fields_rules.py` (`FieldRule`: tokenizable/exemptable per field type), `exemptions.py` (`configure_masking()` path-exemption state, path-prefix matching)
- `pii/` - Keyset-based PII module: `provider.py` (KeysetProvider ABC), `keyset.py` (FileKeysetProvider with hot-reload), `vault.py` (VaultKeysetProvider with AppRole auth), `crypto.py` (HMAC + AES-GCM), `normalize.py` (email/phone normalization; strips wrapping quotes + whitespace before AND after the type-specific normalizer)
- `contrib/django/` - Django-specific middleware and lazy-loading processors, masking boot-check (`checks.py`)
- `contrib/rq/` - RQ job context propagation (decorator-based: `@with_log_context`)
- `contrib/celery/` - Celery task context propagation (signal-based: `install_celery_hooks()`)

## Footguns
- `SAFE_KEYS` whitelist (`masking/patterns.py`) prevents masking of non-PII fields containing "name" etc. (e.g., `service_name`, `pathname`); checked before every other key rule. It holds only names that mean the same in every service — never a service's own vocabulary. A service lists its own in `ECSCTX_MASK_SAFE_KEYS` / `configure_masking_safe_keys()` (`masking/config.py`, resolved like the packs, passed to `classify_key` as `safe`); anything the classifier calls a card, CVV, SAD or credential is refused (`never_safe` asks `classify_key`; expiry is not refused, since nothing masks it). A listed key also frees a digits-only reference number of up to 14 digits from the content rules when the key is not PII on its own and not inside a card/credential/CVV/SAD container (15-19 digits always truncate). Ottu's list is `ecsctx.contrib.ottu.masking.SAFE_KEYS`, opted into by each service, never installed implicitly
- CVV never goes through tokenization at all, even when PII is configured — the CVV rules return the literal `[CVV-MASKED]` directly. PCI forbids storing CVV in any form, not even as an HMAC digest.
- SSN/PEM tokens are computed over a normalized value (digits-only for SSNs, base64-body-only for PEM), not the raw matched text — otherwise the same value in a different grouping/wrapping would produce a different token and break correlation. Card numbers carry no token at all: they truncate to first 6 + last 4 from 15 digits up and last 4 only below (`411111******1111`, bare, PCI DSS 3.5.1, FAQ 1091), separators stripped, independent of PII configuration. The star run is the marker: `already_masked()` and `_text_has_card_context()` both recognise that shape, since there is no wrapper left to read. The card rule (`_CardRun`) reads a whole run of digit groups at once: where a separator admits one card or a card beside another number, Luhn decides, and every Luhn-valid 12-19-digit stretch along the groups lies inside a truncated span (overlapping ones merged), so no output shows more than its first six and last four -- except over digits it leaves as something else's: an IBAN's (its groups joined by single spaces, up to where its check digits hold; after a letter bank code only if they hold at the run's end), a word's own or a truncation's last four (unless they start card-style groups), a phone number's after "+", and a range's across a Unicode dash between non-card-style groups (no stretch crosses it). Accepted residuals follow from those: a card glued to a word or to `****` in non-card-style groups, one split by a range's dash, and the phone rule (it runs first) taking ten digits before a Unicode dash. A later pass leaves a truncation's first six and last four alone. A card key never shows those residuals: it refuses instead.
- No dict-level "already masked" marker: a dict re-passed to `_mask_dict()` (e.g. `mask_sensitive_data` running twice in one chain) is fully re-traversed. Idempotency lives in the leaf checks instead — `mask_by_field_type` leaves an already-`[LABEL…]` value untouched via `already_masked()`, and a second content-regex pass over masked markers is a noop, so `_mask_string` always runs the full pass with no early-exit (a whole-string `already_masked()` gate there would let a coincidental `-MASKED]` fragment suppress masking for real PII in the same string). Only `filter()` marks anything, and only on the `LogRecord` (`mark_object_as_masked`/`is_masked_object`, a plain attribute that never ships as output), so a record reaching two handlers skips masking on the second pass.
- `penc` format includes `kid` for key rotation: `penc:v1:<kid>:<payload>`. All keys in the keyset must be retained for decryption until re-encryption is complete.
