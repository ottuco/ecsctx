# /ecsctx

Core structured logging module with ECS field mapping and PII/PCI masking.

## Entry Points
- `context.py` - `LoggingContext`, `logging_context` context manager, `get_trace_id()`
- `processors.py` - `contextvars_injector`, `mask_sensitive_data` (delegates to `masking.MaskPIIFilter`), `namespace_ecs_fields`
- `masking/` - Unified PII/PCI masking engine: `MaskPIIFilter` (stdlib `logging.Filter`), `install_maskers()`
- `pii/` - PII tokenization (HMAC-SHA-256) and encryption (AES-256-GCM) via keyset files

## Critical Context
- `logging_context` supports nesting - inner contexts merge with outer, auto-restored on exit
- `get_trace_id()` parses W3C traceparent format: extracts 32-char trace-id from `{version}-{trace-id}-{parent-id}-{flags}`
- `PRIMARY_KEYS` in processors.py defines which fields stay at root vs get pushed to `extra`
- Masking has two entry points, both driving the same `MaskPIIFilter`: the filter on every handler `get_logging_config()` builds (masks the record in place — Sentry's logging integration, `handleError` and handlers that never call `format()` read the record) and `mask_sensitive_data` (structlog processor, in the formatter's own chain). The second pass is cheap: `mask_by_patterns` remembers strings already known clean, and a known-clean string is not re-parsed. A string that is a JSON object or list (≤ `JSON_PARSE_LIMIT`, 64 KiB) is parsed and walked with the key rules only, re-serialised only if a key rule changed something, then content-scanned once as text — so a JSON number holding a PAN still masks, as an unquoted marker. Never scanned (`DEFAULT_SKIP_KEYS`, `masking/filters.py`): `service`/`project`/`log` and the correlation ids `session_id`, `trace`, `span`. `user.name` is exempt from the name key rule but content-scanned. The record marker stores the packs that masked it, so a filter with more packs still masks.
- Two independent detection strategies inside `MaskPIIFilter`: 18 ordered content rules (`masking/patterns.py::RULES` — order is load-bearing, see the comments above `_RULE_TABLE`), grouped into packs (`default` always on, the keyed CVV rules 4, 5 and 9 among its own -- their keyword the key rule's CVV words, after `_`/`-`, `card` or a camelCase word (`vpc_CardSecurityCode`, `paymentCvv`), ending the key -- a CVV must not ship from any service, and Connect receives the saved-card CVV; `pci` -- the card rule and the bare-digit CVV rule -- and `financial_ids` opt-in via `masking/config.py`), each behind a literal pre-check; the credential rules (2, 3, 8) and the keyed CVV rules (4, 5, 9) are tried only near their words (`_near_words`: a match starts inside the `[\w-]` run holding its word, at most `_CRED_REACH`/`_CVV_REACH` before it, or on the quote before that run) -- `re.sub` tried every word boundary, and a long `a-a-a-…` cost 0.7 s per CVV rule; and key-name matching (`classify_key()`: substring on the lowercased key, fail closed, EXCEPT the three families where a substring made false positives -- a credential word must end the key (`scheme_token` yes, `schemeTokenProvisioningMode` no), `authorization` must be the whole key (`authorizationCode` is a payment verdict), and a `*name` key is a person's only if a person qualifier is in the name (`customer_name` yes, `domainName` no); a CVV word counts anywhere in the key unless its tail names something about one (`cvv_input` yes -- fail closed -- `cvv_required`/`cardSecurityCodeError` no), matched on the separator-free key; `track`/`magnetic` are SAD only when the rest of the key names the data (`raw_track` yes, `track_id` no), and a key ending in `cryptogram`/`cavv`/`ucaf` is SAD; a national id (`civil_id`, `passport`, `qid`, ...) is `ssn` in every pack; SAFE_KEYS is matched in both spellings, separators or camelCase; card keys matched precisely (`card`, a `pan` word, `cardnumber` in the key, or a key ending `cardno`/`cardnum` -- MIGS's `vpc_CardNum`; `card_id` is an id, not one); expiry is NOT classified and is listed in `SAFE_KEYS`; `sad` (track data, PIN blocks, EMV images, cryptograms) is destroyed outright like CVV and can never be listed safe; cached). A matching key masks its value. A scalar under a non-exemptable type is masked whole (a PAN-shaped credential is the label, never truncated); a CONTAINER under `card`, `cvv`, `sad` or `secret` is walked per leaf (`_WALKED_TYPES`) -- unnamed leaves take the container's type, under `cvv`/`sad` nothing is weaker than the container and only a service-listed key escapes, and a card-shaped object under a credential key is walked as `card` -- spelled out in `_mask_dict` rather than made exemptable, because `exemptable` also governs path exemptions and none of these may ever be whitelistable; a `{name, value}` pair masks `value` by the strictest type its identifiers name (`_pair`); a bare `name` under a container named by a thing (`name_context`) is not a person; booleans are never masked; a dataclass/namedtuple is masked by field then rendered back to repr text; the walk stops at `_MAX_DEPTH` and any exception replaces the message with `[MASKING-FAILED: …]` (a log call must never raise); a dict/list under a PII key (`customer`, `billing`, `contact`, `name`, …) keeps its shape and each field is masked on its own — by its own key's type, kept if a safe key (`id`), else as the container's type — so per-field tokens correlate across records. `exc_info`/`stack_info` are never masked (the rendered `error.*` is). Card keys truncate a PAN value and show what is not one (`mask_card_value`: under 12 digits reads through -- unless a group of digits and stars long enough to be a card number (12+) is in no truncation's shape, `_TRUNCATION_SHAPE`: the first six digits at most, four stars or more, the last four at most -- an upstream system's `123456****7890` and a first-four `4111********1111` included -- with a card number's groups -- four to six digits or stars, one card separator (`_CARD_SEP`) apart, as in 4-4-4-4, Amex 4-6-5 and Diners 4-6-4 -- read as one (`_CARD_GROUPS`), so another masker's `45087****001019` (the last six of 15), `4508-750*-****-1019` (read `4508750*****1019`, the first seven of 16) and `3782 822*** *0005` are refused, while a shorter group ends a run: `**** 1111 12 25` is not judged (`****1111` is eight) -- 12+ is content-scanned for a PAN and refused if none is found, if a run of card-number length is left beside the truncations -- joined by dots or slashes too, and a truncation's first six counting with the digits before it -- or if a Luhn-valid reading the rule leaves in free text shows more than its first six and last four, `_overexposes_a_card`; a value that the scan leaves as it is and that holds a truncation the card rule writes (`_WRITTEN_TRUNCATION`: the first six, stars and last four, or eight stars or more and the last four) -- its own output on a later pass -- is refused only for a card-length run or for digits and stars in any other shape (`_hides_as_truncations`: another masker's `4508750****001019` shows 13 of 17, `****1111 1234 5670` 12 of 16), and the first pass refuses that shape too, so every output is a fixed point (0.15.4 refused its own output there, so the formatter's second pass turned a shown truncation into `[CARD-MASKED]`). A PAN under ANY key is truncated rather than tokenized (`filters._mask_pii_leaf`, gated on `pci`): a keyed hash beside a truncation of the same PAN is what FAQ 1117 forbids, and a card number typed into the name box used to produce exactly that. Under `pci`, a value a PII, secret, ssn or payment-id key would tokenize is its label, not a token, when it holds any 12+ digit run (`holds_pan_run`, fails closed -- a random hex id trips it 2-7% of the time, by length); only in a phone field is a `+`-led run of at most 15 digits (E.164) the phone number. A canonical UUID (`patterns._UUID`: 8-4-4-4-12 hex with at least one hex letter, nothing alphanumeric touching it) is the one exception to "any 12-19 digit run is a card" (the contract `tests/test_masking_false_positives.py` names): a value that is one holds no run, and the card rule leaves its digits as written in text and reads the rest of the run without them, so a card number beside it is still truncated. An all-digit string in that shape gets no exemption.
- A tokenized value is the bare token (`ptok:v1:…`); `[LABEL]` only where no token can stand (tokenization unconfigured/failing, or CVV/card, which are never tokenized; expiry is not masked at all). A null under a sensitive key stays null. `_WHOLE_TOKEN` keeps the credential text rules off a value that is already a token; like `already_tokenized` and `already_masked`, it takes only the exact shape `tokenize` emits (`ptok:v1:` + 43 base64url characters), so anything else typed after `ptok:` is masked -- and it takes none with a card-number run in its body, which `mask_by_field_type` labels. A token followed by `#` is whole: the `#` opens a URL's fragment (`redact_url`'s `?password=<token>#access_token=…`), though `#` is otherwise part of a value. A credential value in text (rules 2, 3 and 8) runs to its delimiter, as a form value in `redact_body` does, never to the end of a fixed character class (a backslash, `@` or apostrophe left the rest in clear): unquoted (`_UNQUOTED_VALUE`), to whitespace, `&`, `;`, `,`, a closing bracket, or a closing quote -- one with nothing of the value after it, or a JSON key's `":` or an element's `/>` -- never starting with a quote or an opening bracket (a container, or a label masking wrote) and never running into a label (`_NOT_A_LABEL`: a `]` would cut it, and a label redact_body wrote after a short value made it long enough to mask again); quoted, to its unescaped closing quote, spaces and all (`_quoted_body`), a `"`-quoted one masked as the JSON string it decodes to (`_mask_quoted`), so it carries the key walk's token. Rule 3 reads a quote as opening a quoted value only when a closing one matches it and something is between them -- quotes doubled as CSV and SQL escape one (`7,"password=""s3cret"""`) are structure before an unquoted value -- and the escaped quotes around a JSON-escaped key as the key's; a value that opens with `\"` (JSON in a JSON string) runs to its matching `\"` as the inner string reads it (`_ESCAPED_QUOTED_UNIT`), spaces and all, masked as it decodes twice (`_mask_escaped_quoted`); `_unquoted_value_quote` escapes the quotes it adds around an unquoted value there. After an Authorization keyword (`_AUTH_KEYWORD`: `authorization`, `Proxy-Authorization`, `authorisation_header`; rule 3 only) the value is the scheme and the credential together (`_AUTH_SCHEME`: bearer, basic, digest, token, negotiate, api-key), so `Authorization: Bearer x` carries the token `mask_secret("Bearer x")` -- the one the header gets under its key -- instead of one token for `Bearer` shared by every record and the credential left to the bare-space rule (which needs a digit: `Basic dXNlcjpwYXNz` shipped); a scheme is never the whole value while more follows it (`Bearer [REDACTED]` stays as it is), and a token after the scheme (`Bearer ptok:v1:…`, what masking the credential alone left) is not hashed again with it. Other keywords take no scheme: `password=basic more words` is the password `basic`. A credential keyword the key rule reads as a CVV or other SAD (`cvv_token`, `pin_password`, `_credential_type`) masks its value as that type, the label, as under the key and in a URL -- never a keyed hash of a CVV. Rule 12 masks a URL's userinfo in text (`scheme://user:password@`, the password possibly empty, or a token alone -- not a user alone, `ssh://git@host`), each part through `_mask_userinfo`, which `contrib.net.redact_url` shares: as it decodes, a token at its head read as the user whole (split at its first colon, pass 2 wrote `ptok:v1:ptok:v1:…`); scheme, host and port kept. It runs before phone and email: a numeric password is no phone number, and the email rule (`_email`) never starts inside masking's own output -- a token, or a userinfo masking wrote (`_mask_userinfo(userinfo) == userinfo`, e.g. redact_url's percent-encoded `%5BSECRET-MASKED%5D`) -- so the host after it survives. A credential keyword as the user (`https://x-access-token:ghp_…@github.com`) is rule 3's first, and the value it runs to takes the host with it. Path exemptions via `configure_masking()`, Django `ECSCTX_MASK_EXEMPT_PATHS`, or env `PII_MASK_EXEMPT_PATHS` (`masking/exemptions.py`, a pattern may start at any depth of the record) apply only to the exemptable field types (email/phone/address/name/generic) and only skip the key-based match — content rules still run on the value (defense in depth). Secrets (cvv/card/secret/payment_id/pem_key/iban/jwt/ssn) are never exemptable.
- PII tokenization supports two providers (`PII_PROVIDER=file|vault`). File provider reads mounted keysets; Vault provider authenticates via AppRole and fetches from KV v2. Access mode (`PII_ACCESS=tokenize|full`) enforces least privilege. Auto-configures lazily from env vars.
- When PII is not configured, `safe_tokenize()` (`masking/tokens.py`, re-exported from `processors`/`ecsctx`; the log-safe wrapper over `pii.tokenize`) returns `[PII_REDACTED]` — `mask_by_field_type()` catches that and falls back to `[LABEL]` rather than embedding it. That fallback is `safe_tokenize`'s documented contract; nothing else emits a fixed marker where a token can stand.
- Every path a credential takes ends in `mask_by_field_type(v, "secret")` — the key walk, the credential text rules, `contrib/django/routes.py`, `contrib/net` — and it returns `[SECRET-MASKED]`, never a token, for a PAN-shaped value (`pan_shaped`, imported inside the function: `patterns` imports `tokens` as it loads) and for a placeholder another masker left (`tokens._PLACEHOLDER`: `[REDACTED]`, `[PII_REDACTED]`, stars, `Bearer ****`), which would otherwise hash into one token shared by every record. With `pci` among the call's packs (`config.packs_in_force()`, imported inside the function as well, since `config` imports `patterns`: the packs of the masking call in progress -- a `MaskPIIFilter`'s own, which every call that builds its context sets in a ContextVar with `config.call_packs` -- and outside a call the process's `get_masking_packs()`), a credential or payment id that holds a card-number run anywhere (`holds_pan_run`) is its label too, on every path -- the text rules, `mask_secret`, `contrib/net`, a route parameter -- as the key walk's own `pci` branch (`filters._mask_pii_leaf`, on `ctx.packs`) makes any PII leaf; without `pci` among the call's packs it is hashed, an accepted residual: a default-pack service receives no card numbers, and the label would stand where a token can for ~7% of Connect's 64-hex HMAC signatures. Masking's own output passes through (`already_masked`) unless a card-number run is in it: `ptok:v1:` typed before a card number is in a token's exact shape, and is the label, for any type and in every pack (`tokens._CARDLESS_TOKEN` is that shape without one; `_WHOLE_TOKEN` takes only it). Both are judged on the value as `tokenize` hashes it (`normalize_value`: surrounding whitespace and one layer of matching quotes dropped), so `'"4111…"'` is not a keyed hash of the bare card number, and on it as a URL or form encoding decodes it (`unquote_plus`, as `redact_url` and `redact_body` read it), so `%224111…%22` or `4111+1111+…` in text is the label in every pack, as a `%5BSECRET-MASKED%5D` redact_url wrote is masked already; and a value that is masking's own output once normalized (a label, token or truncation in quotes, as the credential text rule leaves `password="[SECRET-MASKED]"`) is returned as it is, never hashed into one shared token. `mask_secret(value)` (`masking/patterns.py`, exported from `ecsctx.masking` and `ecsctx` with `mask_card_value`) is that for a value outside a mapping: `None`/bools pass, anything else is masked as `str(value)`. `_mask_pii_leaf` still asks `pan_shaped` for a secret before the `pci` branch, which would truncate it. `contrib/net` masks with `mask_secret` (no `[REDACTED]` since 0.15.4): `redact_url` masks literal `secrets` in one pass, longest first (a replacement is never scanned again, so a short secret can't mangle the token a longer one became), then masks the userinfo part by part (`_mask_userinfo`, a label's brackets percent-encoded: `urlsplit` refuses brackets in a netloc whose host is not IPv6, so the result would not parse again, nor in `ecs_url`) and rewrites a credential query or fragment param in place, unencoded, leaving every other param byte for byte, and rebuilding the URL only when something changed; a query, fragment or form key the key rules call a card, CVV or SAD (`classify_key(unquote_plus(key), ALL_PACKS)`, `_card_field_type`) has its value masked by that type -- `mask_card_value`, or the label, never a token -- in `redact_url` and in `redact_body`'s form pass (`_FORM_FIELD`, run on any body with an `=`, before the credential-key pre-check); `redact_body` reads a JSON value escape-aware, past any escaped character and to the end of the text when no quote closes it (a body `json.loads` rejects is the one that reaches this rule as text), and masks what it decodes to, or the raw text when it does not decode; its closing quote is looked for, not consumed, since in malformed `""password": "…"` it also opens the next key; and a form value runs to the next `&` or whitespace, as in 0.15.3 (every reading that ended it at a quote left the rest of some secret in clear). `_split_form_value` keeps only the structure at its two ends as written -- a quote or an escaped one (at its head, a run of them: `password=""x`, quotes doubled as CSV escapes one), and `}`, `]`, `,`, a JSON key's `":`, `>`, and `/>` after a quote (after an unquoted value a `/` right after a token reads to the credential text rule as more credential, so only `>` stays) -- and takes a label, token, truncation or placeholder followed only by structure whole (`[SECRET-MASKED],` is not `[SECRET-MASKED` and `],`). The value between them is JSON-unescaped only when it sits between escaped quotes (`\"…\"`, in a JSON string; never in a raw form body), is `[SECRET-MASKED]` if it `holds_pan_run` (asked before any pass-through: a token-shaped value can carry a card number), and otherwise goes through `mask_secret`, being written back exactly as captured when that leaves it as it is (empty, or masked already). It is decoded as form encoding reads it (`unquote_plus`: `+` is a space), so outside a form body a secret holding `+` or `%xx` gets a different token than under a key; nothing leaks. The JSON rule gives every value that `holds_pan_run` the same label, closed or run on to the end of the text, before `mask_secret` (which, without `pci`, hashes one that is not in a token's shape).

## Submodules
- `masking/` - `filters.py` (`MaskPIIFilter`, the engine), `patterns.py` (`RULES` content rules and packs, `classify_key()`, `SAFE_KEYS`, `mask_card_value`, `mask_secret`), `config.py` (pack and skip-path selection), `tokens.py` (`safe_tokenize`, `mask_by_field_type`, `already_masked`), `fields_rules.py` (`FieldRule`: tokenizable/exemptable per field type), `exemptions.py` (`configure_masking()` path-exemption state, path-prefix matching)
- `pii/` - Keyset-based PII module: `provider.py` (KeysetProvider ABC), `keyset.py` (FileKeysetProvider with hot-reload), `vault.py` (VaultKeysetProvider with AppRole auth), `crypto.py` (HMAC + AES-GCM), `normalize.py` (email/phone normalization; strips wrapping quotes + whitespace before AND after the type-specific normalizer)
- `contrib/django/` - Django-specific middleware and lazy-loading processors, masking boot-check (`checks.py`)
- `contrib/rq/` - RQ job context propagation (decorator-based: `@with_log_context`)
- `contrib/celery/` - Celery task context propagation (signal-based: `install_celery_hooks()`)

## Footguns
- `SAFE_KEYS` whitelist (`masking/patterns.py`) prevents masking of non-PII fields containing "name" etc. (e.g., `service_name`, `pathname`); checked before every other key rule. It holds only names that mean the same in every service — never a service's own vocabulary. A service lists its own in `ECSCTX_MASK_SAFE_KEYS` / `configure_masking_safe_keys()` (`masking/config.py`, resolved like the packs, passed to `classify_key` as `safe`); anything the classifier calls a card, CVV, SAD or credential is refused (`never_safe` asks `classify_key`; expiry is not refused, since nothing masks it). A listed key also frees a digits-only reference number of up to 14 digits from the content rules when the key is not PII on its own and not inside a card/credential/CVV/SAD container (15-19 digits always truncate). Ottu's list is `ecsctx.contrib.ottu.masking.SAFE_KEYS`, opted into by each service, never installed implicitly
- CVV never goes through tokenization at all, even when PII is configured — the CVV rules return the literal `[CVV-MASKED]` directly. PCI forbids storing CVV in any form, not even as an HMAC digest.
- SSN/PEM tokens are computed over a normalized value (digits-only for SSNs, base64-body-only for PEM), not the raw matched text — otherwise the same value in a different grouping/wrapping would produce a different token and break correlation. Card numbers carry no token at all: they truncate to first 6 + last 4 from 15 digits up and last 4 only below (`411111******1111`, bare, PCI DSS 3.5.1, FAQ 1091), separators stripped, independent of PII configuration. The star run is the marker: `already_masked()` and `_text_has_card_context()` both recognise that shape, since there is no wrapper left to read. The card rule (`_CardRun`) reads a whole run of digit groups at once: where a separator admits one card or a card beside another number, Luhn decides, and every Luhn-valid 12-19-digit stretch along the groups lies inside a truncated span (overlapping ones merged), so no output shows more than its first six and last four -- except over digits it leaves as something else's: an IBAN's (`_iban_end`: its country's registered length from `_IBAN_LENGTHS`, in groups of four joined by single spaces, check digits holding; after a letter bank code only if the IBAN ends where the run does), a word's own or a truncation's last four (unless they start a Luhn-valid card in card-style groups, which makes them a card's), a phone number's after "+" (at most 15 digits, E.164, even a card's), a range's across a Unicode dash (no stretch crosses it; a Unicode dash is a separator only when the whole run is card-style groups), and a canonical UUID's (`_UUID`; the run is read again without them, `_truncated_outside`). Accepted residuals follow from those: a card glued to a word or to `****` in non-card-style groups, one split by a range's dash, a card completing an IBAN of its country's exact length with check digits holding, a card typed into a UUID's own groups (`41111111-1111-1111-abcd-ef0123456789` stays whole in free text, and under a name key with a keyset it is hashed), and the phone rule (it runs first) taking phone-shaped digits at a card's end (ten before a Unicode dash, or its last digits with those after them). A later pass leaves a truncation's first six and last four alone. A card key never shows those residuals: it refuses instead.
- No dict-level "already masked" marker: a dict re-passed to `_mask_dict()` (e.g. `mask_sensitive_data` running twice in one chain) is fully re-traversed. Idempotency lives in the leaf checks instead — `mask_by_field_type` leaves an already-`[LABEL…]` value untouched via `already_masked()`, and a second content-regex pass over masked markers is a noop, so `_mask_string` always runs the full pass with no early-exit (a whole-string `already_masked()` gate there would let a coincidental `-MASKED]` fragment suppress masking for real PII in the same string). Only `filter()` marks anything, and only on the `LogRecord` (`mark_object_as_masked`/`is_masked_object`, a plain attribute that never ships as output), so a record reaching two handlers skips masking on the second pass.
- `penc` format includes `kid` for key rotation: `penc:v1:<kid>:<payload>`. All keys in the keyset must be retained for decryption until re-encryption is complete.
