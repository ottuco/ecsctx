# /ecsctx

Core structured logging module with ECS field mapping and PII/PCI masking.

## Entry Points
- `context.py` - `LoggingContext`, `logging_context` context manager, `get_trace_id()`
- `processors.py` - `contextvars_injector`, `mask_sensitive_data` (delegates to `masking.MaskPIIFilter`), `namespace_ecs_fields`
- `masking/` - Unified PII/PCI masking engine: `MaskPIIFilter` (stdlib `logging.Filter`), `install_maskers()`
- `pii/` - PII tokenization (HMAC-SHA-256) and encryption (AES-256-GCM) via keyset files

## Critical Context
- `logging_context` supports nesting - inner contexts merge with outer, auto-restored on exit
- `get_trace_id()` parses W3C traceparent format: extracts 32-char trace-id from `{version}-{trace-id}-{parent-id}-{flags}`
- `PRIMARY_KEYS` in processors.py defines which fields stay at root vs get pushed to `extra`
- Masking has two entry points, both driving the same `MaskPIIFilter`: the filter on every handler `get_logging_config()` builds (masks the record in place — Sentry's logging integration, `handleError` and handlers that never call `format()` read the record) and `mask_sensitive_data` (structlog processor, in the formatter's own chain). The second pass is cheap: `mask_by_patterns` remembers strings already known clean, and a known-clean string is not re-parsed. What a rule set derives -- its known-clean set, `scalar_rules`, its distinct gates -- is cached on the tuple's identity (`patterns._by_identity`), never on its hash: hashing a tuple of rules hashes every compiled pattern's whole program, on every call (30 µs a string for the default pack; lru_cache paid it on every lookup, the 0.15.5 slowdown, #160054). A string that is a JSON object or list (≤ `JSON_PARSE_LIMIT`, 64 KiB) is parsed and walked with the key rules only, re-serialised only if a key rule changed something, then content-scanned once as text — so a JSON number holding a PAN still masks, as an unquoted marker. Never scanned (`DEFAULT_SKIP_KEYS`, `masking/filters.py`): `service`/`project`/`log` and the correlation ids `session_id`, `trace`, `span`. `user.name` is exempt from the name key rule but content-scanned. The record marker stores the packs that masked it, so a filter with more packs still masks. A record `getMessage()` could not render once masked -- a %-style template masking changes (`password=%s`: rule 7 reads the placeholder as the credential), a msg that is not a str (a lazy translation, an exception; `_template_of` is `str(msg)`, bytes decoded as masking decodes them (as `str(bytes)` it never matched the masked template, so every bytes record lost its args), None for a dict or list, a structured record, whose args, if any, stay as they are -- logging cannot format it, so as in stdlib the line is dropped and `handleError` prints the args, masked (README says so)), a number masking turned into text under `%d` (`_as_masked_text` reads that conversion as `%s`, keeping its key, `-`, width and `*`s, so the masked text renders where the number stood; rendered from the raw number, a card number glued to a word stays whole; it finds the conversion by counting them as CPython's `%` reads a template (`_CONVERSION`: `%%`, a key to its balancing parenthesis, flags, width, a precision whose digits may be none -- `%.f` -- one length modifier), else the count slipped and the record was the marker), args that never fit, or a line that masks differently from its masked args rendered (a value split between template and arg, `cvv=%s` with `123`) -- is rendered from the masked args and masked whole, its args `()` (`MaskPIIFilter._mask_rendered`), or is the `[MASKING-FAILED: …]` marker: before, `getMessage()` raised, the handler dropped the line and `handleError` printed the args to stderr. It renders from the masked args, not the raw ones, so a dict arg is still masked by its keys (from the raw ones a card number under `card_number` reached only the text rules, and the default pack has no card rule). A template masking leaves as it is, that renders, and whose masked args render a line with nothing more to mask, keeps its args, and Sentry's grouping by it. Rendered, a record keeps no args for a later handler to mask with more packs, so the render path masks them with every pack (`ALL_PACKS`, only for a record that takes it): a default handler ahead of a pci one rendered `ref4111…` whole, glued to a word, for the pci handler to log, in a pci process and in a default one. A record that keeps its args is masked piece by piece, and the line its masked args render holds nothing more to mask: readers besides the formatter (Sentry's logging integration, `handleError`, a handler that never calls `format()`) render it themselves, and a value split between template and arg (`cvv=%s` with `123`) no longer reaches them as `cvv=123` -- that record takes the render path (`install.py`'s docstring says so). The check renders and masks the line once per record with args; the formatter's `mask_sensitive_data` masks the same line again, a known-clean lookup when it matches.
- Two independent detection strategies inside `MaskPIIFilter`: 24 ordered content rules (`masking/patterns.py::RULES` — order is load-bearing, see the comments above `_RULE_TABLE`), grouped into packs (`default` always on, the value rule 2, the XML card, CVV and SAD element 3 and credential element 4, the `API-Key` scheme 6, the credential container 8 and the keyed CVV rules 9, 10 and 14 among its own -- their keyword the key rule's CVV words, after `_`/`-`, `card` or a camelCase word (`vpc_CardSecurityCode`, `paymentCvv`), ending the key -- a CVV must not ship from any service, and Connect receives the saved-card CVV; `pci` -- the card rule and the bare-digit CVV rules, 23 beside a card number or its truncation and 24 after a CVV word -- and `financial_ids` opt-in via `masking/config.py`), each behind a literal pre-check; the credential rules (5, 6, 7, 8, 13) and the CVV word rules (9, 10, 14, 24) are tried only near their words (`_near_words`: a match starts inside the `[\w-]` run holding its word, at most `_CRED_REACH`/`_CVV_REACH` before it, or on the quote before that run) -- `re.sub` tried every word boundary, and a long `a-a-a-…` cost 0.7 s per CVV rule; and key-name matching (`classify_key()`: substring on the lowercased key, fail closed, EXCEPT the three families where a substring made false positives -- a credential word must end the key (`scheme_token` yes, `schemeTokenProvisioningMode` no), `authorization` must be the whole key (`authorizationCode` is a payment verdict), and a `*name` key is a person's only if a person qualifier is in the name (`customer_name` yes, `domainName` no); a CVV word counts anywhere in the key unless its tail names something about one (`cvv_input` yes -- fail closed -- `cvv_required`/`cardSecurityCodeError` no), matched on the separator-free key; `track`/`magnetic` are SAD only when the rest of the key names the data (`raw_track` yes, `track_id` no), and a key ending in `cryptogram`/`cavv`/`ucaf` is SAD; a national id (`civil_id`, `passport`, `qid`, ...) is `ssn` in every pack; SAFE_KEYS is matched in both spellings, separators or camelCase; card keys matched precisely (`card`, a `pan` word, `cardnumber` in the key, or a key ending `cardno`/`cardnum` -- MIGS's `vpc_CardNum`; `card_id` is an id, not one); expiry is NOT classified and is listed in `SAFE_KEYS`; `sad` (track data, PIN blocks, EMV images, cryptograms) is destroyed outright like CVV and can never be listed safe; cached). A matching key masks its value. A scalar under a non-exemptable type is masked whole (a PAN-shaped credential is the label, never truncated); a CONTAINER under `card`, `cvv`, `sad` or `secret` is walked per leaf (`_WALKED_TYPES`) -- unnamed leaves take the container's type, under `cvv`/`sad` nothing is weaker than the container and only a service-listed key escapes, and a card-shaped object under a credential key is walked as `card` -- spelled out in `_mask_dict` rather than made exemptable, because `exemptable` also governs path exemptions and none of these may ever be whitelistable; a `{name, value}` pair masks `value` by the strictest type its identifiers name (`_pair`); a bare `name` under a container named by a thing (`name_context`) is not a person; booleans are never masked; a dataclass/namedtuple is masked by field then rendered back to repr text; the walk stops at `_MAX_DEPTH` and any exception replaces the message with `[MASKING-FAILED: …]` (a log call must never raise); a dict/list under a PII key (`customer`, `billing`, `contact`, `name`, …) keeps its shape and each field is masked on its own — by its own key's type, kept if a safe key (`id`), else as the container's type — so per-field tokens correlate across records. `exc_info`/`stack_info` are never masked (the rendered `error.*` is). Card keys truncate a PAN value and show what is not one (`mask_card_value`: under 12 digits reads through -- unless a group of digits and stars long enough to be a card number (12+) is in no truncation's shape, `_TRUNCATION_SHAPE`: the first six digits at most, four stars or more, the last four at most -- an upstream system's `123456****7890` and a first-four `4111********1111` included -- with a card number's groups -- four to six digits or stars, one card separator (`_CARD_SEP`) apart, as in 4-4-4-4, Amex 4-6-5 and Diners 4-6-4 -- read as one (`_CARD_GROUPS`), so another masker's `45087****001019` (the last six of 15), `4508-750*-****-1019` (read `4508750*****1019`, the first seven of 16) and `3782 822*** *0005` are refused, while a shorter group ends a run: `**** 1111 12 25` is not judged (`****1111` is eight) -- 12+ is content-scanned for a PAN and refused if none is found, if a run of card-number length is left beside the truncations -- joined by dots or slashes too, and a truncation's first six counting with the digits before it -- or if a Luhn-valid reading the rule leaves in free text shows more than its first six and last four, `_overexposes_a_card`; a value that the scan leaves as it is and that holds a truncation the card rule writes (`_WRITTEN_TRUNCATION`: the first six, stars and last four, or eight stars or more and the last four) -- its own output on a later pass -- is refused only for a card-length run, for twelve digits or more showing beside its truncations (`_digits_beside_truncations`) or around one (`_card_digits_showing`), or for digits and stars in any other shape (`_hides_as_truncations`: another masker's `4508750****001019` shows 13 of 17, `****1111 1234 5670` 12 of 16), and the first pass refuses that shape too, so every output is a fixed point (0.15.4 refused its own output there, so the formatter's second pass turned a shown truncation into `[CARD-MASKED]`). A PAN under ANY key is truncated rather than tokenized (`filters._mask_pii_leaf`, gated on `pci` among the call's packs and the process's, as is a bare int card number: in a pci process a default filter hashed one typed into the name box): a keyed hash beside a truncation of the same PAN is what FAQ 1117 forbids, and a card number typed into the name box used to produce exactly that. Under `pci`, a value a PII, secret, ssn or payment-id key would tokenize is its label, not a token, when it holds any 12+ digit run (`holds_pan_run`, fails closed -- a random hex id trips it 2-7% of the time, by length); only in a phone field is a `+`-led run of at most 15 digits (E.164) the phone number. An email or phone number the text rules find is judged the same way (`tokens._PAN_CHECKED_TYPES`: secret, payment_id, email, phone; a phone as written, `phone=True`), so with `pci` `4111111111111111@example.com` and `+4111111111111111` are their labels, not keyed hashes. A canonical UUID (`patterns._UUID`: 8-4-4-4-12 hex with at least one hex letter, nothing alphanumeric touching it) is the one exception to "any 12-19 digit run is a card" (the contract `tests/test_masking_false_positives.py` names): a value that is one holds no run, and the card rule leaves its digits as written in text and reads the rest of the run without them, so a card number beside it is still truncated. An all-digit string in that shape gets no exemption.
- A tokenized value is the bare token (`ptok:v1:…`); `[LABEL]` only where no token can stand (tokenization unconfigured/failing, or CVV/card, which are never tokenized; expiry is not masked at all). A null under a sensitive key stays null. `_WHOLE_TOKEN` keeps the credential text rules off a value that is already a token; like `already_tokenized` and `already_masked`, it takes only the exact shape `tokenize` emits (`ptok:v1:` + 43 base64url characters), so anything else typed after `ptok:` is masked -- and it takes none with a card-number run in its body, which `mask_by_field_type` labels. A token followed by `#` is whole: the `#` opens a URL's fragment (`redact_url`'s `?password=<token>#access_token=…`), though `#` is otherwise part of a value. A credential value in text (rules 5, 7 and 13) runs to its delimiter, as a form value in `redact_body` does, never to the end of a fixed character class (a backslash, `@` or apostrophe left the rest in clear), and never into an end tag (`_NOT_AN_END_TAG`; a quoted value neither, `_quoted_value_body`: in `<note>password=abc</note>` it took `</note` and the next pass hashed its token again): unquoted (`_UNQUOTED_VALUE`), to whitespace, `&`, `;`, `,`, a closing bracket, or a closing quote -- one with nothing of the value after it, or a JSON key's `":` or an element's `/>` -- never starting with a quote or an opening bracket (a container, or a label masking wrote) and never running into a label (`_NOT_A_LABEL`: a `]` would cut it, and a label redact_body wrote after a short value made it long enough to mask again); quoted, to its unescaped closing quote, spaces and all (`_quoted_body`), a `"`-quoted one masked as the JSON string it decodes to (`_mask_quoted`), so it carries the key walk's token. Rule 7 reads a quote as opening a quoted value only when a closing one matches it and something is between them -- quotes doubled as CSV and SQL escape one (`7,"password=""s3cret"""`) are structure before an unquoted value -- and the escaped quotes around a JSON-escaped key as the key's; a value that opens with `\"` (JSON in a JSON string) runs to its matching `\"` as the inner string reads it (`_ESCAPED_QUOTED_UNIT`), spaces and all, masked as it decodes twice (`_mask_escaped_quoted`); `_unquoted_value_quote` escapes the quotes it adds around an unquoted value there. After an Authorization keyword (`_AUTH_KEYWORD`: `authorization`, `Proxy-Authorization`, `authorisation_header`; rule 7 only) the value is the scheme and the credential together (`_AUTH_SCHEME`: bearer, basic, digest, token, negotiate, api-key), so `Authorization: Bearer x` carries the token `mask_secret("Bearer x")` -- the one the header gets under its key -- instead of one token for `Bearer` shared by every record and the credential left to the bare-space rule (which needs a digit: `Basic dXNlcjpwYXNz` shipped); a scheme is never the whole value while more follows it (`Bearer [REDACTED]` stays as it is), and a token after the scheme (`Bearer ptok:v1:…`, what masking the credential alone left) is not hashed again with it. Rule 6 does the same for Ottu's `API-Key` scheme word standing alone, without its `Authorization:` (not ending a header name, `X-API-Key`): the scheme and any value to its delimiter -- no digit or length guard, the word is the evidence (1 in 1,550 of Ottu PG's Fernet keys has no digit) -- are one value, `mask_secret("API-Key <key>")`, the header's token; it runs before rule 7, which would otherwise mask a `password=` inside the value first, and leaves a field masking wrote there (`API-Key password=<token>`). Rule 13 leaves a value whose digits are all in masking's own output (a whole token, a label, a truncation): `Bearer password=<token>`, which redact_body wrote, was hashed again, a token of a token; a credential glued to a key name keeps its own digits (`Token abc123abc123api_key=…`) and is still hashed. Rule 8 masks a container after a credential keyword whole (`password=['a', 'b']`, a rendered `%(pw)s`; a repr's quoted key keeps it a string), bracket-aware and nested three deep, or to the end of the line when never closed -- not after a JSON key (the key walk masked that container by its keys: the saved card under `token`), nor one holding only masking's own output (`_masked_already`, a record's field). Rule 3 masks an XML element named as the key walk names a card, CVV or SAD (`mask_card_elements`: `classify_key` on its local name, every pack on), in every pack: a CVV's or SAD's text, children and all, its label; a card's text a card value (`mask_card_value`: a test card that fails Luhn truncated without `pci`), and a card object (`<card>` holding elements, CyberSource's) field by field -- a CVV or SAD element its label, every other element's text a card value, so `<accountNumber>` truncates and an expiry reads through. It runs before rule 4, so a `<cvv>` inside `<password>` is its label, not part of the text the credential's token hashes. Rule 4 masks an XML element named by a credential keyword (`<wsse:Password>…</wsse:Password>`), to its end tag, children and all, as it decodes (`_element_text`: CDATA, entities); a start tag no end tag closes is no element (a route, `/v1/cards/<str:token>/`). Rules 3 and 4 are walks, not regexes (`_mask_elements`; the pattern hands the walk the text from its first `<`): a text's end tags are indexed once (`_end_tags`) and a start tag's found by name -- a lazy regex looked for one from every start tag, and 160 KB of `<password>` took 12 s. Rule 2 gives a JSON object a service's label rule matches first (value rules, below), written as JSON or a repr in text or as JSON in a JSON string, the rule's label, quoted where it was a JSON value; the key walk does to one as a mapping or JSON text under any key (`filters._value_ruling`), and to JSON text holding one deeper under a key that would hash or show it (`label_within`). Before every rule, `mask_by_patterns` sets aside what a keep rule ships (`stash_kept`, below). Other keywords take no scheme: `password=basic more words` is the password `basic`. A credential keyword the key rule reads as a CVV or other SAD (`cvv_token`, `pin_password`, `_credential_type`) masks its value as that type, the label, as under the key and in a URL -- never a keyed hash of a CVV. Rule 17 masks a URL's userinfo in text (`scheme://user:password@`, the password possibly empty, or a token alone -- not a user alone, `ssh://git@host`, unless it is shaped like a card number or holds a card-number run: then `[SECRET-MASKED]`, as redact_url gives it), each part through `_mask_userinfo`, which `contrib.net.redact_url` shares: as it decodes, a token at its head read as the user whole (split at its first colon, pass 2 wrote `ptok:v1:ptok:v1:…`); scheme, host and port kept. It runs before phone and email: a numeric password is no phone number, and the email rule (`_email`) never starts inside masking's own output -- a token, or a userinfo masking wrote (`_mask_userinfo(userinfo) == userinfo`, e.g. redact_url's percent-encoded `%5BSECRET-MASKED%5D`) -- so the host after it survives. A credential keyword as the user (`https://x-access-token:ghp_…@github.com`) is rule 7's first, and the value it runs to takes the host with it. Path exemptions via `configure_masking()`, Django `ECSCTX_MASK_EXEMPT_PATHS`, or env `PII_MASK_EXEMPT_PATHS` (`masking/exemptions.py`, a pattern may start at any depth of the record) apply only to the exemptable field types (email/phone/address/name/generic) and only skip the key-based match — content rules still run on the value (defense in depth). Secrets (cvv/card/secret/payment_id/pem_key/iban/jwt/ssn) are never exemptable.
- PII tokenization supports two providers (`PII_PROVIDER=file|vault`). File provider reads mounted keysets; Vault provider authenticates via AppRole and fetches from KV v2. Access mode (`PII_ACCESS=tokenize|full`) enforces least privilege. Auto-configures lazily from env vars.
- When PII is not configured, `safe_tokenize()` (`masking/tokens.py`, re-exported from `processors`/`ecsctx`; the log-safe wrapper over `pii.tokenize`) returns `[PII_REDACTED]` — `mask_by_field_type()` catches that and falls back to `[LABEL]` rather than embedding it. That fallback is `safe_tokenize`'s documented contract; nothing else emits a fixed marker where a token can stand.
- Every path a credential takes ends in `mask_by_field_type(v, "secret")` — the key walk, the credential text rules, `contrib/django/routes.py`, `contrib/net` — and it returns `[SECRET-MASKED]`, never a token, for a PAN-shaped value (`pan_shaped`, imported inside the function: `patterns` imports `tokens` as it loads) and for a placeholder another masker left (`tokens._PLACEHOLDER`: `[REDACTED]`, `[PII_REDACTED]`, stars, `Bearer ****`), and for a truncation the card rule writes (`tokens._SHOWN_TRUNCATION`, `411111******1111` as written or decoded, or any truncation after an auth scheme, `tokens._TRUNCATION_AFTER_A_SCHEME`, `Bearer 411111******1111`, which was a token of the two: ten digits of a saved card's gateway token, which never passes through as masking's own output -- rendered from its argument under pci, `token=%s` showed them where the key walk gave the label), which would otherwise hash into one token shared by every record. With `pci` among the call's packs, and the process's (`config.packs_in_force()`, imported inside the function as well, since `config` imports `patterns`: the packs of the masking call in progress -- a `MaskPIIFilter`'s own, which every call that builds its context sets in a ContextVar with `config.call_packs` -- joined with the process's `get_masking_packs()`, so in a pci-configured process every filter labels such a value, a filter built with pci labels it in any process, and a default handler ahead of a pci one no longer hashes what the pci handler then logs), a credential, payment id, email or phone number that holds a card-number run anywhere (`holds_pan_run`; a phone's `+`-led run up to 15 digits is the number) is its label too, on every path -- the text rules, `mask_secret`, `contrib/net`, a route parameter -- as the key walk's own `pci` branch (`filters._mask_pii_leaf`, on the call's packs and the process's, `filters._pci_in_force`) makes any PII leaf; without `pci` among the call's packs and the process's it is hashed, an accepted residual: a default-pack service receives no card numbers, and the label would stand where a token can for ~7% of Connect's 64-hex HMAC signatures. Masking's own output passes through (`already_masked`) unless a card-number run is in it: `ptok:v1:` typed before a card number is in a token's exact shape, and is the label, for any type and in every pack (`tokens._CARDLESS_TOKEN` is that shape without one; `_WHOLE_TOKEN` takes only it). Both are judged on the value as `tokenize` hashes it (`normalize_value`: surrounding whitespace and one layer of matching quotes dropped), so `'"4111…"'` is not a keyed hash of the bare card number, and on it as a URL or form encoding decodes it (`unquote_plus`, as `redact_url` and `redact_body` read it), so `%224111…%22` or `4111+1111+…` in text is the label in every pack, as a `%5BSECRET-MASKED%5D` redact_url wrote is masked already; and a value that is masking's own output once normalized (a label, token or truncation in quotes, as the credential text rule leaves `password="[SECRET-MASKED]"`) is returned as it is, never hashed into one shared token. `mask_secret(value)` (`masking/patterns.py`, exported from `ecsctx.masking` and `ecsctx` with `mask_card_value`) is that for a value outside a mapping: `None`/bools pass, anything else is masked as `str(value)`. `_mask_pii_leaf` still asks `pan_shaped` for a secret before the `pci` branch, which would truncate it. `contrib/net` masks with `mask_secret` (no `[REDACTED]` since 0.15.4): `redact_url` masks literal `secrets` in one pass, longest first (a replacement is never scanned again, so a short secret can't mangle the token a longer one became), then masks the userinfo part by part (`_mask_userinfo`, a label's brackets percent-encoded: `urlsplit` refuses brackets in a netloc whose host is not IPv6, so the result would not parse again, nor in `ecs_url`) and rewrites a credential query or fragment param in place, unencoded, leaving every other param byte for byte, and rebuilding the URL only when something changed; a query, fragment or form key the key rules call a card, CVV or SAD (`classify_key(unquote_plus(key), ALL_PACKS)`, `_card_field_type`) has its value masked by that type -- `mask_card_value`, or the label, never a token -- in `redact_url` and in `redact_body`'s form pass (`_FORM_FIELD`, run on any body with an `=`, before the credential-key pre-check); `redact_body` reads a JSON value escape-aware, past any escaped character and to the end of the text when no quote closes it (a body `json.loads` rejects is the one that reaches this rule as text), and masks what it decodes to, or the raw text when it does not decode; its closing quote is looked for, not consumed, since in malformed `""password": "…"` it also opens the next key; and a form value runs to the next `&`, whitespace or end tag (`_FORM_VALUE`), as in 0.15.3 but for the tag (every reading that ended it at a quote left the rest of some secret in clear). `redact_body` first gives every value a service's label rule matches its label (`patterns.mask_objects`, rule 2's pattern) and sets aside what a keep rule ships (`patterns.stash_kept`; an element's entity-encoded text that keeps one is set aside whole, `KeptStash.hold`, since base64's `==` after a run holding `cvv` reads as a CVV form field), then reads an XML element as a key (`_mask_xml_elements`): its local name, whatever its namespace prefix and attributes -- first a card, CVV or SAD name, as rule 3 reads one (`patterns.mask_card_elements`: a card object field by field, so a `<cvv>` inside `<card>` is its label), then a credential name (`_is_credential_key`, or a secret body key) as a credential, the label when it holds a card-number run -- one classification across a URL's query and an XML body, so `<auth>`, `<user>`, `<sign…>` and `<key>` are credentials, as those query params are; the text runs to the end tag, children and all, as it decodes; a start tag no end tag closes is no element; a leaf holding JSON or XML written with entities goes through `redact_body` as it decodes and is written back escaped (only those: a form body's `&amp;` is its separator where it stands, and decoded, a form value read differently on the next pass). `_split_form_value` keeps only the structure at its two ends as written -- a quote or an escaped one (at its head, a run of them: `password=""x`, quotes doubled as CSV escapes one, and a run of two or more of either kind, `password=''x` -- a lone `'` is the value's own, a quoted value when another closes it), and `}`, `]`, `,`, a JSON key's `":`, `>`, and `/>` after a quote (after an unquoted value a `/` right after a token reads to the credential text rule as more credential, so only `>` stays) -- and takes a label, token, truncation or placeholder followed only by structure whole (`[SECRET-MASKED],` is not `[SECRET-MASKED` and `],`). The value between them is JSON-unescaped only when it sits between escaped quotes (`\"…\"`, in a JSON string; never in a raw form body), is `[SECRET-MASKED]` if it `holds_pan_run` (asked before any pass-through: a token-shaped value can carry a card number), and otherwise goes through `mask_secret`, being written back exactly as captured when that leaves it as it is (empty, or masked already). It is decoded as form encoding reads it (`unquote_plus`: `+` is a space), so outside a form body a secret holding `+` or `%xx` gets a different token than under a key; nothing leaks. The JSON rule gives every value that `holds_pan_run` the same label, closed or run on to the end of the text, before `mask_secret` (which, without `pci`, hashes one that is not in a token's shape). When its credential passes change the text, `redact_body` runs its card/CVV/SAD field pass once more: masking a credential can uncover a field the first pass read as part of the one holding it (`"password": "password="paymentCvv=…`), so one call leaves nothing a second would mask. The text rules then `redact_body` are a fixed point (0.15.6: the scheme word's rule leaves `password=<token>`, a quoted value stops at an end tag, and only JSON or XML leaves are decoded; on 280k generated shapes none changed on a second pass, where 0.15.5 missed 240 of 120k).

- `masking/` - `filters.py` (`MaskPIIFilter`, the engine), `patterns.py` (`RULES` content rules and packs, `classify_key()`, `SAFE_KEYS`, `mask_card_value`, `mask_secret`), `config.py` (pack and skip-path selection, a service's safe keys and value rules), `value_rules.py` (`ValueRule`: a service's own shapes of value, masked as their label), `tokens.py` (`safe_tokenize`, `mask_by_field_type`, `already_masked`), `fields_rules.py` (`FieldRule`: tokenizable/exemptable per field type), `exemptions.py` (`configure_masking()` path-exemption state, path-prefix matching)
- `pii/` - Keyset-based PII module: `provider.py` (KeysetProvider ABC), `keyset.py` (FileKeysetProvider with hot-reload), `vault.py` (VaultKeysetProvider with AppRole auth), `crypto.py` (HMAC + AES-GCM), `normalize.py` (email/phone normalization; strips wrapping quotes + whitespace before AND after the type-specific normalizer)
- `contrib/django/` - Django-specific middleware and lazy-loading processors, masking boot-check (`checks.py`)
- `contrib/rq/` - RQ job context propagation (decorator-based: `@with_log_context`)
- `contrib/celery/` - Celery task context propagation (signal-based: `install_celery_hooks()`)

## Footguns
- `SAFE_KEYS` whitelist (`masking/patterns.py`) prevents masking of non-PII fields containing "name" etc. (e.g., `service_name`, `pathname`); checked before every other key rule. It holds only names that mean the same in every service — never a service's own vocabulary. A service lists its own in `ECSCTX_MASK_SAFE_KEYS` / `configure_masking_safe_keys()` (`masking/config.py`, resolved like the packs, passed to `classify_key` as `safe`); anything the classifier calls a card, CVV, SAD or credential is refused (`never_safe` asks `classify_key`; expiry is not refused, since nothing masks it). A listed key also frees a digits-only reference number of up to 14 digits from the content rules when the key is not PII on its own and not inside a card/credential/CVV/SAD container (15-19 digits always truncate). Ottu's list is `ecsctx.contrib.ottu.masking.SAFE_KEYS`, opted into by each service, never installed implicitly
- Value rules (`masking/value_rules.py`): a service's own shapes of value, masked as their label (label rules) or shipped as sent (keep rules) wherever they are logged; ecsctx names none. `ECSCTX_MASK_VALUE_RULES` / `configure_masking_value_rules()` (`masking/config.py`, resolved like the safe keys: rule objects, or dotted import paths to a rule or a collection, comma-separated in the env var; an item that is not one -- a rule with both a `field_type` and `keep = True` included -- raises from the call, is dropped with a warning from the setting or env var, and fails the boot check). A label rule has `field_type` (the label, `make_label`), `matches(mapping)` and optional `hints` (literal strings its text holds one of: a rule is never asked about text holding none, `applicable`; the key walk of JSON text passes on only those, `_mask_json_text`). A keep rule (`KeepRule`, or `keep is True` with a callable `matches`) writes no label: what it matches ships as sent. One list, asked in its order, the first match winning (`_first_match`; each rule's kind is cached on the tuple's identity, `_split`) -- for the value itself: a value strictly inside a keep match whose own first match is a label rule (listed before any keep rule matching it) is labelled and the keep refused (`keep_refused`: the guard, or `label_within` over its members, asked only with a label rule among the rules, a label rule's error refusing the keep and raising nothing; called from `ruling` and rule 2). The engine asks them about every mapping the key walk meets under any key, every JSON-text string (`_value_ruling` -> label, `KEEP` or None; JSON text holding a label match deeper under a key that would hash it is the label, `label_within`, which looks into a keep match like any mapping, a kept one holding no label: JSON text holding a kept value deeper is still hashed whole), every JSON object in text (rule 2 for label rules, `_OBJECT_TEXT`: JSON, a repr, or JSON in a JSON string, three levels deep; an object no rule matches is read member by member) and every such object in a body (`redact_body` -> `patterns.mask_objects`, first). A label match is the rule's label, never hashed. A keep match is a deep copy in the key walk, not descended into; in text `mask_by_patterns` replaces it with a `[KEPT-<letters>-MASKED]` placeholder before every rule (`stash_kept`/`kept_spans`, top down: a label match is no span; and no span at all in text that names a CVV/SAD key anywhere -- `floored_text`, read only once a span is found: a quoted key then `:`/`=`/`=>`, a bare key then `:`/`=>`, a key and `=` where a key starts (not base64 padding in a string), an XML tag, or a `{name, value}` pair's label, `classify_key(..., ALL_PACKS, safe keys)`, as written and entity-decoded; fails closed, a sibling's value too, since the text rules read objects only three levels deep; `redact_body` passes it to an entity-encoded leaf, `_encoded_leaf(keep=False)`) and restores each placeholder still there; a placeholder is named from a blake2b digest of its value (`_placeholder`, 14 letters: the same value one name in any text, so a credential hashed around it carries that value in its token, and `restore` fills only its own names, so a name written into the text restores nothing; two values whose names collide are masked as without a keep rule); a keep decision on text rests on the text as written (`json_as_written` refuses a key written twice, `_written_as_parsed` keeps a repr only where it renders back exactly); restored text is not recorded clean, and text holding `[KEPT-` is masked as before. Never kept: under a CVV/SAD key, inside a CVV/SAD container (a listed key there reads through with the label rules only, `_without_keep`), the `value` of a pair labelled as one (`_floored`); nor a match holding a card/CVV/SAD key, a `{name, value}` pair labelled as one, or a card number at any depth, JSON text inside included -- keys, pairs, whole leaves, and a card number's digits inside a text leaf that is no JSON text (`patterns.holds_card_run`: `holds_pan_run`, 12+ digits joined by single separators, as the pci rules read a value, one linear pass with a bytes-translate fast path for base64; not read in a leaf that is a whole hex id of 24+ characters holding a hex letter, `_HEX_ID` fullmatch -- Apple Pay's 64-hex ids; Ottu's base64 slots refuse hex alone, 1.1% of which hold a Luhn run -- nor a leaf that is epoch milliseconds); a CVV or other short value inside a longer string is the matcher's to keep out (`holds_card_data`: a string leaf is a card number when `pan_shaped`, either way except 13 bare digits from a 1 or 2 -- epoch milliseconds, Google Pay's `keyExpiration`, which `pan_shaped` reads as one), which is walked as if nothing matched. A keep matcher that raises is no match (it runs in `redact_url`/`redact_body`/`mask_card_value`); a label matcher's error leaves the marker. `is_kept`/`mask_outside_kept` (`ecsctx.masking`) serve a service's own pass after ecsctx's. Configuring the value rules empties `patterns._clean`. Nothing configured, nothing runs: the rules are looked up only when a mapping, JSON text or text holding `{` asks, at most once a call in the key walk (`_Pass.values`).
- CVV never goes through tokenization at all, even when PII is configured — the CVV rules return the literal `[CVV-MASKED]` directly. PCI forbids storing CVV in any form, not even as an HMAC digest.
- SSN/PEM tokens are computed over a normalized value (digits-only for SSNs, base64-body-only for PEM), not the raw matched text — otherwise the same value in a different grouping/wrapping would produce a different token and break correlation. Card numbers carry no token at all: they truncate to first 6 + last 4 from 15 digits up and last 4 only below (`411111******1111`, bare, PCI DSS 3.5.1, FAQ 1091), separators stripped, independent of PII configuration. The star run is the marker: `already_masked()` and `_text_has_card_context()` both recognise that shape, since there is no wrapper left to read. The card rule (`_CardRun`) reads a whole run of digit groups at once: where a separator admits one card or a card beside another number, Luhn decides, and every Luhn-valid 12-19-digit stretch along the groups lies inside a truncated span (overlapping ones merged), so no output shows more than its first six and last four -- except over digits it leaves as something else's: an IBAN's (`_iban_end`: its country's registered length from `_IBAN_LENGTHS`, in groups of four joined by single spaces, check digits holding; after a letter bank code only if the IBAN ends where the run does), a word's own or a truncation's last four (unless they start a Luhn-valid card in card-style groups, which makes them a card's), a phone number's after "+" (at most 15 digits, E.164, even a card's), a range's across a Unicode dash (no stretch crosses it; a Unicode dash is a separator only when the whole run is card-style groups), and a canonical UUID's (`_UUID`; the run is read again without them, `_truncated_outside`). Accepted residuals follow from those: a card glued to a word or to `****` in non-card-style groups, one split by a range's dash, a card completing an IBAN of its country's exact length with check digits holding, a card typed into a UUID's own groups (`41111111-1111-1111-abcd-ef0123456789` stays whole in free text, and under a name key with a keyset it is hashed), and the phone rule (it runs first) taking phone-shaped digits at a card's end (ten before a Unicode dash, or its last digits with those after them). A later pass leaves a truncation's first six and last four alone. A card key never shows those residuals: it refuses instead, since `mask_card_value` shows its scan only while fewer than twelve digits show outside the truncations the card rule writes, however they are joined -- double spaces, commas, another masker's `X`s (`_digits_beside_truncations`, group by group: a search for the shape from every star of a long run was quadratic). Nor may twelve digits show in a row, however joined (`_card_digits_showing`, one running count): bare digits, a truncation's last four and the next one's first six count together, as a card number could be read across them; a truncation's own stars separate its first six from its last four; a word ends a row, but a run of `X`/`x` joins digits as stars do (another masker's `4508750XXX001019`). So `4111111111  111111******1111`, `400001******5018  00  000009******0001` (the Maestro 501800000009), `********4111  ********1111  1111`, `02313379 ********1262`, `411111******3782XX82246310005`, `512345******0008 12 25 512345******0008` and `4111111111111111 12345678901` are refused. The one residual left: a short group beside a truncation, under twelve digits with it (`450875******1019 000` could be a 19-digit number another masker cut oddly).
- No dict-level "already masked" marker: a dict re-passed to `_mask_dict()` (e.g. `mask_sensitive_data` running twice in one chain) is fully re-traversed. Idempotency lives in the leaf checks instead — `mask_by_field_type` leaves an already-`[LABEL…]` value untouched via `already_masked()`, and a second content-regex pass over masked markers is a noop, so `_mask_string` always runs the full pass with no early-exit (a whole-string `already_masked()` gate there would let a coincidental `-MASKED]` fragment suppress masking for real PII in the same string). Only `filter()` marks anything, and only on the `LogRecord` (`mark_object_as_masked`/`is_masked_object`, a plain attribute that never ships as output), so a record reaching two handlers skips masking on the second pass.
- `penc` format includes `kid` for key rotation: `penc:v1:<kid>:<payload>`. All keys in the keyset must be retained for decryption until re-encryption is complete.
